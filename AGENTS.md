# Repo Instructions For Codex

This file defines how Codex should work in this repository for all future conversations.

## Project Context

- This repository is the portfolio website of an industrial designer.
- The primary audience is recruiting companies and design agencies.
- The website should support hiring outcomes: clarity, polish, strong presentation, and thoughtful storytelling.
- The user is not interested in web development details unless they are useful for making a decision.

## Collaboration Style

- Be collaborative, warm, and solution-oriented.
- Keep explanations occasional and practical rather than technical by default.
- Avoid unnecessary web-development jargon.
- Preserve the user's writing tone unless explicitly asked to rewrite it.
- If something may hurt hiring outcomes, say so clearly and respectfully.

## Decision-Making Rules

- For bigger decisions, offer options first before making changes.
- If there are multiple good options, ask the user first instead of choosing on your own.
- If a situation is confusing or ambiguous, stop and ask.
- For non-design improvements, keep the user informed but do not ask for permission too often.

## What Counts As A Bigger Design Decision

Ask before changing any of the following:

- Page layout or section structure
- Color usage
- Spacing rhythm
- Animation style or motion behavior
- Copy hierarchy or content structure
- Overall visual direction

Font changes do not automatically require approval under this rule, but they should still be handled carefully and in line with the current design language unless the user asks otherwise.

## Design Change Policy

- Default to the current design language unless the user explicitly asks to change it.
- Check `DESIGN_LANGUAGE.md` before making any UI or visual changes.
- Do not introduce design changes silently.
- If a design change is approved and implemented, update `DESIGN_LANGUAGE.md` to reflect the new baseline.
- Stick to the visual references, colors, fonts, and patterns already used in the repo unless the user directs otherwise.

## Working Style

- The user will usually describe what they want, and Codex should implement it directly.
- Prefer making the change instead of explaining how the user could do it.
- Keep the user informed while working, especially when making non-design improvements such as bug fixes, performance improvements, accessibility fixes, or SEO basics.
- Balance speed and polish, and surface the tradeoff when it matters for a task.

## Communication During Tasks

- Share concise progress updates.
- When useful, include a short `Things To Consider` section with genuinely helpful adjacent ideas the user may want to think about.
- Do not overload the user with implementation detail unless they ask.

## Quality Bar

- Prioritize a portfolio experience that feels intentional, polished, and consistent.
- Protect the existing design language and visual coherence.
- Favor maintainable, stable solutions over clever ones.
- Keep the experience professional and recruiter-friendly across desktop and mobile.
